# Melba v0.3.22 — a queue that cannot play stops instead of spinning

Melba v0.3.22 is a patch release on the same **glibc 2.35** baseline. It fixes a
defect that filled a disk.

## 14 GB of `queue-writes.jsonl`

One install reached 62 million lines — 14 GB — in
`~/.local/state/melba/queue-writes.jsonl`, still growing at about 11 MB a second
while the daemon sat paused. Two things produced that.

**A recorder nobody read any more.** Every queue write appended a line naming the
process that wrote it, to attribute a bug where a test had replaced the saved
queue. That class is prevented structurally now — tests resolve their own state
directory, and the daemon is handed the app's directories — so the recorder was
answering a question nobody asks, forever, at one line per write. It is gone.

**Unbounded writes behind it.** A queue whose every track fails to open advanced
to the next entry, and each advance rewrote `queue.json` as well. 62 million
lines is 62 million advances: the loop was walking a queue nothing in it could
play, as fast as it could.

## What happens now

- When every track in the queue has been tried and none could be opened, playback
  stops with the reason recorded (`open: no track in the queue could be played`),
  instead of advancing again.
- The state file is written at most once every two seconds, forced when the
  process quits, so a future tight loop cannot rewrite it as fast as it turns.
- Nothing writes a file beside user state to watch another file.

Both are held by tests: the play loop must keep the failure counter, and
`ci/test_no_runaway_state.py` fails if the removed filename appears in any source
again, or if the throttle decision stops being one testable function.

## Compatibility evidence

Same as v0.3.13 through v0.3.21: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
