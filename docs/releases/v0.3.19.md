# Melba v0.3.19 — claims that had to be true

Melba v0.3.19 is a patch release on the same **glibc 2.35** baseline. Most of it
is about statements the program makes: what it trusts, what it calls a
pass-through, where it keeps a token, and what its logs and configuration mean.
One of the statements was false, which is how it was found.

## `PASSTHROUGH` was reported for a device the session does not carry

`melbad play --device null --verify` reported `PASSTHROUGH`. That verdict is a
claim about the stream PipeWire carries — no converters, no other client, the
stream rate equal to the source rate, at most 24 bits — and `null` is not in the
session graph at all. The graph was found by name, so the check picked up
**another melbad process's** stream and applied it to this one.

The verdict now requires the device to be the one PipeWire owns (`default`).
`hw:`, `plughw:`, `null` and paths are devices this process opened itself, and
the session graph says nothing about them. Found by the existing test that
asserts the receipt never claims an exclusive path for `--device null`, which
had started failing because the claim had become false.

## One trusted update key instead of two

Updates are accepted only when `checksums.txt` carries a signature from the
pinned Ed25519 key. A second key had been left in `additional_publisher_keys`
from the v0.3.2 key change: that field is the place for the *next* key during a
rotation, and holding a retired key there meant anyone with it could sign an
update this build would install. It is empty now, and every release from
v0.3.13 through v0.3.18 verifies against the pinned key alone.

## The token file is checked, not assumed

The MusicKit token still lives in a `0600` file in a `0700` directory — no
keyring dependency, for the reasons written down in
[Security](security.md) — but the permissions are now read rather than assumed.
A file others can read, a directory they can enter, or a symlink in place of the
file is reported on stderr and by `melbad auth status`. It keeps working: the
exposure already happened, and locking someone out would not undo it.

Anyone who does keep tokens in a keyring or a password manager can supply it
instead:

```sh
export MELBA_MUSIC_USER_TOKEN_CMD='secret-tool lookup service melba'
```

## Logs and configuration say what they are

- `melbad` diagnostics are events: `level=warn event=alac_fallback
  reason="wrapper unreachable"`, or one JSON object per line with
  `MELBA_LOG=json`. This is the format `wrapper.log` needed to be parseable at
  all.
- `wrapper.log` is now rotated to `wrapper.log.1` when the wrapper starts. The
  failure message says "see wrapper.log", and restarting used to delete exactly
  that file.
- `config.json` is read as a struct instead of free-form JSON. Keys this build
  does not know are kept and written back, and an unrecognised `wrapper_mode`
  reads as the external one rather than failing the file.
- `mk`'s catalogue summary names its keys once (`Item`/`Attributes`) instead of
  indexing them by string ten times; the JSON it prints is unchanged, with one
  deliberate difference: a field whose value is `null` is omitted rather than
  repeated as `null`.

## Documentation

[docs/security.md](security.md) records what is stored, what it grants, and what
is out of scope. [SECURITY.md](../SECURITY.md) covers reporting and release-key
rotation, including the two-step dance the pinned key requires.
[docs/environment.md](environment.md) lists the variables that change behaviour
and says plainly that there is no `.env` file, because nothing reads one.

## Compatibility evidence

Same as v0.3.13 through v0.3.18: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
