# Melba v0.3.18 — a queue row that looks like the song

Melba v0.3.18 is a patch release on the same **glibc 2.35** baseline. It finishes
the queue work v0.3.17 started, and gives a playlist that has no artwork
something to show.

## A row the player only half described

The daemon names the queue slots the player has reached and nothing more: on
this machine's saved queue that was **42 names for 301 slots**. The rest are
named by asking the catalogue, which is why a row could sit there with a label
and a note icon and never improve.

Two things were stopping that request.

- A row that had a name but no cover and no length was taken as resolved,
  because "has a name" was the whole test. Now a row counts as resolved only if
  it also carries a length, an album or artwork.
- Any cache hit was treated as the answer. A cache entry with no cover and no
  length is the same gap the row has, so keeping it meant the one request that
  would have filled it never went out — for the whole session. An entry now
  counts only if it describes the song.

A lookup that fails is remembered for five minutes, so a song the catalogue
cannot answer for does not turn into one request per frame.

## A playlist with no artwork

Every playlist you make has no artwork from the service, and the tile showed a
flat placeholder. It now gets a cover derived from its name: two hues from a
hash of the name, the same cover every time, with the playlist glyph over it.
Home tiles and the library grid both use it, so the same playlist looks the
same in both places.

## What still has no cover, on purpose

Some songs are published without artwork. `875196654`, for instance, resolves
with its artist and album but no image. Melba draws the note placeholder there
rather than inventing a picture: the honest answer is that the service never
sent one.

## Compatibility evidence

Same as v0.3.13 through v0.3.17: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
