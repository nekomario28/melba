# Melba v0.3.17 — the queue names its songs

Melba v0.3.17 is a patch release on the same **glibc 2.35** baseline. It fixes
two things a screenshot caught: queue rows labelled with an id, and a second
tile for the same songs on Home.

## `stream:1538278608` is not a song title

Rows in the queue showed an id with no cover. The songs themselves were fine —
`melbad mk song` resolves every one of the ids that appeared — so the failure
was not in the catalogue lookup but in the label the app was handed, and three
places had to agree to produce it:

- the player filled an unnamed queue slot's title with the key it held, and for
  a song that key is `stream:<id>`
- the worker passed that string on as a name, and separately parsed the cover
  the player reports per slot and dropped it
- the app treated a non-empty name as "already resolved", so it never asked
  which song the row was

The player no longer invents a title from a URI (a file path still supplies its
stem, because that is its name), the worker carries the cover, and the app
treats a `stream:<id>` label as unnamed — so the row asks for its song and
fills in title, artists and album.

Rows that already showed a name but no cover suffered only the middle defect,
and are fixed by the same change.

## Home offered the same songs twice

Home always prepended a tile for Liked Songs, and once the daemon had identified
the account's own Favorites playlist and the library listed it, the screen
offered that playlist twice: the synthetic tile and the real one. The synthetic
tile now steps aside when the playlist it stands for is present. Where the
account has no such playlist, the tile keeps its place, because then it is the
only way in.

The sidebar is unchanged.

## Compatibility evidence

Same as v0.3.13 through v0.3.16: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
