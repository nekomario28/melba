# Melba v0.3.20 — sign-in that works on the wrapper's own loader

Melba v0.3.20 is a patch release on the same **glibc 2.35** baseline. It carries
one fix, contributed as a pull request: the credential never arrived when the
Android rootfs called the preload shim before it had set up its arguments.

## The shim ran before there were arguments to scrub

`melbad wrapper login` execs the wrapper with a placeholder (`-L @`) and the real
`user:pass` in a memfd; a preloaded library replaces that placeholder in memory,
so the password never appears in `/proc/<pid>/cmdline`. On the staged rootfs,
bionic can run that library's `.init_array` **before** it has set `argc`,
`argv` and `envp`, so the shim received garbage (an `argc` of 262984144 and
unrelated pointers), found no `-L`, left the placeholder in place, and the
wrapper exited 0 without attempting a login. `melbad wrapper login` then
reported `argv-scrub.so did not take effect`.

The real argument block is now recovered from `/proc/self/stat` field 28
(`startstack`), which is where the kernel put it. When it cannot be recovered,
nothing is repointed and the login fails closed exactly as before — the fix
cannot turn a broken login into a silent one.

The shim's protocol marker moves to `melba-login-fd-v3`. That used to mean
re-running `melbad wrapper setup` for a file this binary already ships, so
`melbad wrapper login` now rebuilds an out-of-date shim from the source it
carries, and only refuses when there is no compiler to do it with.

## Tests that hold it

- the field arithmetic is compiled into a harness from the shim's own source and
  driven with a complete line, a truncated one, and a line without field 28;
  `comm` carries a space and parens so the count has to skip past the last `)`
- the embedded source and the marker the binary accepts must agree, which fails
  if either side moves without the other
- a stale shim is rebuilt and the login proceeds; a shim that cannot be built is
  refused and the wrapper is not spawned

## Compatibility evidence

Same as v0.3.13 through v0.3.19: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
