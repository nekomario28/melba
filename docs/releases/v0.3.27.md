# Melba v0.3.27 — emptying the queue, on purpose

Melba v0.3.27 is a patch release on the same **glibc 2.35** baseline.

## `ctl clear` keeps the current song, and `clear-all` does not

`MelbaQueueClear` empties the queue but keeps the track at the cursor — the
"clear what is coming up" action a player offers, and the reason a stopped daemon
still showed one entry afterwards. That is the right default, but it read as
broken when what was meant was "empty everything".

`melbad ctl clear-all` (MPRIS `MelbaQueueEmpty`) clears the array, resets the
cursor and the play order, and stops playback, so the queue is empty on disk and
on screen. Measured on a paused daemon holding two entries: `clear` leaves 1,
`clear-all` leaves 0 with the cursor at 0 and playback stopped.

The help text and the function's comment say which is which.

## Dependencies

`sha2` 0.11, `wry` 0.57, `cc` 1.11, `log` 0.4.35, `clap` 4.6.7, `thiserror`
2.0.21, `serde_json` 1.0.154, `crc32fast` 1.5.4, `flate2` 1.1.11 and
`actions/cache` v6. `sha2` 0.11 needed one edit: its digest no longer formats as
`{:x}`, so the playlist-cover cache key hex-encodes the bytes itself — the digest
is unchanged. `ureq` 3 is not part of this: it rewrites the client API and needs
its own slice.

## Notes on the history rewrite

The authorship rewrite of 2026-11-10 is recorded in the update notes: every
commit after the rewritten one has a new SHA while the trees are identical, and
the release tags still point at the commits they were published from.

## Compatibility evidence

Same as v0.3.13 through v0.3.26: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.
