# Melba v0.3.16 — a verified shared path gets its own word

Melba v0.3.16 is a patch release on the same **glibc 2.35** baseline. It adds
one verdict, fixes one silent failure, and finishes a surface that was being
sent to the daemon and dropped there.

## Shared output that measurably passes through unchanged

PipeWire output used to report `SHARED` whatever the session graph was doing,
so the one strong claim — `BITPERFECT`, an exclusive device this app opened and
can read back — had to carry every weaker case as a qualifier. It now has a
separate word.

`PASSTHROUGH` is reported when the stream reaches the sink through a shared
graph that the session itself describes as unmodified: no converter nodes on
the path, this stream is the only client, the stream rate equals the source
rate, and no more than 24 bits. The graph is re-read every five seconds, so a
second client joining drops the verdict back to `SHARED` without restarting
playback.

The claim rests on a measurement, not on the absence of a mixer: an isolated
`melbad play --device default` at 48 kHz/24-bit to an HDMI sink produced 88 768
frames that were bit-identical in both channels to the source, with gain
exactly 1.000000000 — a float round trip that is exact at 24 bits. That measures
the sink monitor of one configuration. It is not a DAC-side measurement, and
other sample rates, other graphs and other hardware are not covered by it.

## `melbad play --device default` played nothing

The command zeroed its frame count whenever the verdict was not `BITPERFECT`,
a leftover from when only the exclusive path was allowed. So the shared path
opened the device, reported the format, and played no audio at all. Only
`--require-bitperfect` refuses a shared output now, and the receipt says "not
bit-perfect" instead of claiming the playback was refused.

`melbad doctor` also prints what the session graph says about the stream, so
`PASSTHROUGH` can be checked against `pw-dump` rather than taken on trust.

## A stale login shim repairs itself

`login` refuses to start unless the preload shim that keeps the Apple ID
password out of `/proc/<pid>/cmdline` matches the binary. Bumping that
protocol's marker therefore asked every ALAC user to run `melbad wrapper setup`
again for a file the binary already carries. The source is embedded now, and
login rebuilds the shim with `cc` when the installed one is out of date. A
machine without a compiler still refuses, and says so.

## Commands the daemon used to drop

Seven commands were being sent and discarded by the worker's catch-all: the
liked-songs cache, the library and home caches, the per-playlist cache, opening
the themes folder, and the artwork accent. They are implemented — the playlist
cache is versioned and keyed by account and snapshot, and the app validates the
snapshot before adopting it — and a guard now fails when a new command variant
has no handler.

Network status is derived from what requests actually did rather than from a
probe, so a captive portal or a server error is not reported as being offline.

## Publication

The retired repository name no longer appears in the translation catalogs, the
bug-report address or the packaging metadata, and the captured evidence files
carry placeholders instead of a user name and a LAN address.

Dependencies moved with the release: `jsonschema` 0.58→0.60, `tao`
0.34→0.37, `jiff`, `ron`, `objc2`, `cc`, `libc` and `roxmltree`, plus
`upload-artifact` v7 and `download-artifact` v8. `base64` 0.23 and `tiny-skia`
0.12 stay where they are: the request stack and `resvg` still require the older
versions, and neither can move alone.

## Compatibility evidence

Same as v0.3.13 through v0.3.15: the published archives need at most
`GLIBC_2.35` (`melba`) and `GLIBC_2.34` (`melbad`), the workflow executes the
candidates in Debian 12/13, Ubuntu 22.04/24.04/26.04, Fedora 43/44 and Arch
containers, and it installs the signed release with `install-release.sh` in
five of them.

This is launch and shared-library compatibility only — not Apple sign-in,
desktop rendering, physical audio output or ALAC playback, and not a
run-verification of ARM64 on target hardware.

## Still required on the user's machine

Unchanged: AAC-256 needs a Widevine CDM already installed by Chrome, Chromium or
Vivaldi, and ALAC needs a FairPlay decrypt service the user supplies.
`melbad doctor` reports both.
